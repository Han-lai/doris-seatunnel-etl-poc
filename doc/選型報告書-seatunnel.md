## 3.1.1 Seatunnel 評估 

### 3.1.1.1 Seatunnel 簡介 
 SeaTunnel是一個開源的輕量級分佈式資料集成平台，用於批處理和流式資料的高效處理、轉換和集成。支持多種資料源和資料目標，處理資料的導入、導出、轉換、過濾和聚合等任務，以其高擴展性和穩定性，成為數據集成和處理的強大解決方案。
 ![](/uploads/upload_6466d8465116f5fe5859fc19875d3ec3.png)
 
SeaTunnel具備 Source、Transform 和 Sink 三大核心功能：

* Source 
    * 定義：
      用於定義數據來源的組件，負責從外部系統中提取數據。
    * 特性：
        * 支援多種數據來源，如關係型資料庫、分布式消息系統、雲存儲和文件系統。
        * 可配置讀取方式（批量或實時），以適應不同的業務場景。
        * 支援多種數據格式（例如 JSON、CSV、Avro、Parquet）。
    * 常見數據來源：
        * 關係型數據庫：MySQL、PostgreSQL、SQL Server 等
        * 大數據存儲：HDFS、Hive、Amazon S3
        * 消息系統：Kafka、RabbitMQ
        * 文件格式：CSV、JSON、Parquet
* Transform  
    * 定義：
      用於處理數據的模塊，負責對數據進行清洗、轉換、聚合或其他操作。
    * 特性：

        * 支援靈活的數據轉換邏輯，適合複雜的數據清洗與處理需求。
        * 提供多種內建的轉換功能，例如字段篩選、字段計算、數據類型轉換。
        * 支援多步驟的數據處理流程設計，可組合使用多個轉換模塊。
    * 常見的轉換操作：
        * 字段篩選：只選擇需要的字段。
        * 字段計算：基於現有字段進行數值計算或字符串操作。
        * 數據清洗：處理缺失值、無效數據或異常值。
        * 字段合併與拆分：合併多個字段為一個，或拆分單個字段為多個。
        * 數據聚合：按條件進行統計計算（如總和、平均值）定義：

* Sink 
    * 定義 :
     SeaTunnel 用於定義數據存儲目標的組件，負責將處理後的數據寫入到指定的目標系統中。
    * 特性：
        * 支援多種數據目標，如數據庫、文件系統、大數據處理系統等。
        * 可配置寫入方式（實時或批量），滿足不同的性能需求。
        * 支援分區、格式化數據和自定義字段映射。

 #### Source 測試階段說明：
Src_Kafka 從 Kafka Topic 消費數據

1. 設定SeaTunnel JOB模式 
- **Batch** 和 **Stream** 模式
主要通過運行模式和調度邏輯的控制來區分，根據任務配置決定是一次性完成還是持續運行。
    *  Batch 和 Stream 的主要區別
        * Batch 模式：在特定的 Offset 範圍內進行消費，處理完成後流程結束，不持續監控新的數據。
        * Stream 模式：持續消費新消息，並根據配置的 Offset 策略（如 Earliest 或 Latest）動態處理 Kafka 中的新數據。

2. 確保 SeaTunnel 正確連接到 Kafka 集群：

- **測試 SASL 認證**（如 `SASL/PLAIN` 或 `SASL/SCRAM`），確保 SeaTunnel 能夠成功完成身份驗證並連接到 Kafka 集群：
  - **SASL/PLAIN 認證方式**：確保 SeaTunnel 能正確處理用戶名和密碼的身份驗證配置（`security.protocol=SASL_PLAINTEXT` 和 `sasl.mechanism=PLAIN`）。
  - **PLAINTEXT 傳輸方式**（未設置認證配置）：確認在無加密和身份驗證的情況下，SeaTunnel 能正常提取數據。


 3. 確保 SeaTunnel 成功訂閱並消費指定的 Topic：
在測試過程中，我們觀察到 SeaTunnel 對 Kafka Topic 名稱的解析具有明確的邏輯規則，SeaTunnel 預設以句點 「.」 分割 Topic 名稱，並將其映射為資料庫名稱和表格名稱。這提供了一個簡潔且高效的方式來將 Kafka Topic 映射到資料庫與表格。然而，在某些複雜命名結構中，這一邏輯可能需要進一步調整以滿足特定業務場景的需求。

- **Kafka Topic 解析邏輯**：
SeaTunnel 的解析邏輯基於對 Topic 名稱中句點（.）的分隔，這在常見命名規範（`<database>.<table>` 或 `<schema>.<table>`）中運行良好。對於具有更多層次命名的場景，則需要一些額外的配置或規範調整，以充分發揮其潛力。

    - **建議採用標準化命名結構**：  
    通過簡化 Kafka Topic 的命名方式，不僅可以最大限度發揮 SeaTunnel 預設解析邏輯的效能，還能提升系統的可讀性與易維護性：

        * 推薦命名結構：`<database>.<table>` 或 `<schema>.<table>`
        * 範例：
            `sales.orders`（簡單且直觀）
            `inventory.products`（符合業務邏輯）    
    
4. 驗證 SeaTunnel 提取的數據與 Kafka Topic 中的數據完全一致，無遺漏或重複 ：

    - 確保 SeaTunnel 消費並處理的數據與 Kafka 中的原始數據完全一致，沒有遺漏或重複的情況。

5. **Kafka 測試結果**：
    SASL/PLAIN 和 SASL/SCRAM 配置均測試成功，數據提取穩定，無丟失或錯誤訊息。
    在高負載場景下（每秒 10,000 條訊息），SeaTunnel 表現良好，處理延遲在可接受範圍內。

#### sink 階段說明
在本次測試中，驗證sink中三個模塊在seatunnel Doris Sink Connector的功能，評估連接器的穩定性、功能完整性。

4. doris.batch.size
doris.batch.size 定義了每次通過 HTTP 請求向 Doris 寫入數據的批量大小。當緩存的行數達到此設定值，或者任務執行到 checkpoint 時，數據將會被批量提交到 Doris。
* 確認在不同的 doris.batch.size 配置下，數據寫入的性能表現和穩定性。
* 驗證在小批次與大批次提交情況下，是否會影響 Doris 的吞吐量、數據正確性及資源使用效率。
* 評估批次大小對緩存策略的影響，特別是在高頻率數據寫入場景中的行為。

| Batch size | 寫入性能 | 資源消耗 | 數據正確性 | 穩定性 |
| ---------- | -------- | -------- | ---------- | ------ |
| 100       | 延遲較低，但總處理時間較長 |  Doris 請求次數較多，資源消耗較高 | 數據正確性高            | 	高頻寫入場景可能導致過多連接請求 |
| 1024 (默認值)     |  性能均衡，總處理時間和延遲均可接受        | 資消耗適中         |   數據正確性高        |   	穩定性良好     |
| 10000    | 	批次寫入吞吐量高，但延遲較長     |   Doris 的內存壓力較大       | 數據正確性高           |  在極高頻寫入時可能會產生間歇性延遲  |

* 最佳配置建議：`doris.batch.size=1024` 對大多數場景提供良好的性能和穩定性。
* 特殊場景調整：
    小批次寫入（100）：適用於低延遲需求場景，但需注意網絡開銷。
    大批次寫入（10000）：適用於高吞吐量場景，但需檢查 Doris 資源及seatunnel資源是否充足。
* 優化建議：
    Doris 服務端可通過調整內存緩存配置（如 `load_mem_limit`）提高處理大批次的能力。
    測試高頻寫入場景時，需確保網絡穩定性，避免請求丟失。

#### 結論 :

Seatunnel: Seatunnel 是一個用於數據同步、轉換的開源工具，它能夠從各種數據源（如數據庫、消息隊列等）中提取數據，並將其轉換為目標格式。Seatunnel 的特點之一是它在轉換過程中能夠處理各種數據結構並將其映射到目標欄位上。因此，Seatunnel 可以保持每個原始資料欄位的結構，將其準確地傳送到目標端。

測試指標說明   

(以下參考用, 根據目前實測和環境做刪減)   

列出對調度工具的核心評估維度： 

#### 功能性 
1. 功能特性

* 支援的數據來源和目標系統範圍（連接器數量和類型）。
* 支援批量與流式處理的能力。
* 數據轉換的靈活性（字段映射、清洗等）。
2. 效能
* 是否能穩定處理大規模數據。
* 是否滿足實時數據處理需求。
3. 維護性
* 配置是否簡單易用。
* 是否提供可視化界面或配置文件支持。
* Log 和監控工具的豐富程度。
4. 擴展性
* 是否支持多節點擴展和分布式架構。
* 能否輕鬆添加新的連接器或自定義模塊。
5. 穩定性與錯誤處理
* 異常情況下是否能進行重試或自動恢復。
* 對數據一致性的保證機制（如事務支持）。
6. 安全性
* 是否支援加密數據傳輸與用戶身份驗證。
